 # ゲーム開発言語セレクター

 言語の選択は、ハード制約を設定から分離した後でのみ行ってください。既存のエンジンまたはコードベースで言語が修正されている場合は、書き換えを提案するのではなく、その制約を確認してください。

 ## 意思決定入力

 - 既存のエンジン、ソース言語、ビルド パイプライン、プラグイン、出荷されたコード
- ターゲット プラットフォームとストアまたはコンソールの制限
- ゲームのスケール、シミュレーション密度、レイテンシー、メモリ、読み込み、および決定論のニーズ
- チームの経験、採用、イテレーション速度、デバッグ、ツール、ミドルウェア、およびメンテナンスの期間
- ネットワーク権限、モッディング/スクリプトのニーズ、ネイティブ統合、および展開モデル

 ## ワークフロー

 1. まず既存のプロジェクトの証拠を検出します。ユーザーが明示的に移行分析を要求しない限り、確立されたエンジンと言語のペアはロックされているものとして扱います。
2. 要件を厳密な制約、重み付けされた設定、および未知数に変換します。プロファイリングの証拠なしに、生の言語速度を出荷時のゲームのパフォーマンスと同一視しないでください。
3. 互換性のないオプションを削除し、プラットフォーム サポート、エンジンの成熟度、ライブラリ、イテレーション、実行時の動作、運用、チーム リスクに関して残りの候補を比較します。
4. 決定的な証拠がある場合は、主要な推奨事項を 1 つ返します。それ以外の場合は、ランク付けされた候補リストを返し、不確実性を解決する最小のプロトタイプまたはベンチマークに名前を付けます。
5. マッチング エンジン スキルにルーティングします。必要に応じて、ゲームプレイ スクリプト、ネイティブ拡張機能、シェーダー、ビルド スクリプト、およびバックエンド サービスを個別の言語決定として保持します。

 ## コントラクト

 レポート `primary`、`alternatives`、`locked_by_engine`、`confidence`、`reasons`、`tradeoffs`、および `validation` を出力します。ターゲット エンジンがサポートしていないエンジンと言語の組み合わせを決して考え出さないでください。

 ## 境界

 別の言語のスコアが高いという理由だけで、既存のプロジェクトを移行したり、ランタイムを追加したり、ビルド ツールを変更したりしないでください。このような変更には、明示的な移行リクエストと、プラグイン、アセット、保存、CI、プラットフォーム認証、ロールバックをカバーする証拠が必要です。
